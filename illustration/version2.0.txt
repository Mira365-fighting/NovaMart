# NovaMart v2.0 —— 前后台分离 + 完整登录态 + Vue3 前端

> 本版在 v1.0（注册 / 登录 / 商品 / 购物车 / 订单的纯 CRUD）之上做了四件大事：
> **完整登录态**（黑名单退出 + 双 Token + ThreadLocal）、**商品缓存**（Redis 回归）、
> **前后台分离**（用户端 / 管理端 + 角色鉴权）、**并发安全的下单**（事务 + 行锁），
> 并新增 **Vue3 + Element Plus 响应式前端**。

---

## 一、需求

1. **登录态做完整**
   - 退出登录时把 Token 写入 Redis 黑名单，过滤器逐个请求校验；
   - Refresh Token 机制：短 Token 2 小时 + 长 Token 7 天，短 Token 过期靠长 Token 无感续期；
   - 拦截器统一解析，userId 放进 ThreadLocal，业务层直接取。
2. **商品模块 + Redis 缓存**
   - 商品详情缓存 `product:{id}`，miss 则查库再 SET（基础 TTL 30 分钟）；
   - 查不到的商品也缓存 NULL，TTL 5 分钟 —— 防缓存穿透；
   - 基础 TTL 上叠加 0~10 分钟随机量 —— 防缓存雪崩；
   - 商品列表加分页。
3. **前后台分离**
   - 前台：商品搜索（按名称模糊）、分类筛选、订单状态流转（取消 / 确认收货）；
   - 后台（Admin）：商品 CRUD、订单管理（发货 / 关闭）、用户管理；
   - 用 `@PreAuthorize("hasRole('ADMIN')")` 区分前后台权限；
   - 所有列表接口统一分页参数。
4. **购物车 / 订单优化**
   - 购物车合并：登录后把 localStorage 里的临时购物车合并进 DB；
   - 订单创建纳入事务（`@Transactional`，创建订单 + 扣库存原子化）；
   - 库存扣减改用数据库行锁 `SELECT ... FOR UPDATE`。
5. 把本版引入的依赖和配置文件结构写进本文档。
6. 加入 **Vue3 + Element Plus** 构建响应式页面。

## 五、关键实现

### 1. 完整登录态

**双 Token**：一次登录签发两个 Token，靠 `typ` 声明区分，两个校验器各自绑定 `typ`，
所以拿 refreshToken 当 accessToken 用会直接校验失败。

| Token | 有效期 | 作用 |
| --- | --- | --- |
| accessToken | 2h | 每个请求放在 `Authorization: Bearer <...>` |
| refreshToken | 7d | 只在 accessToken 过期后换新的一对 |

`POST /api/user/refresh` 换 Token 时做**轮换**：旧的 refreshToken 用完立刻拉黑。
这样长 Token 被窃取后重复使用会失败，风险窗口从 7 天缩小到「一次使用」。

**Redis 黑名单**：JWT 是无状态的，签发出去收不回来，所以退出登录只能在服务端记一笔。

- key 用 **jti**（Token 唯一标识）而不是整串 Token，`jwt:blacklist:{jti}`；
- **TTL = Token 的剩余有效期** —— 过期后 key 自动消失，黑名单不会无限膨胀；
- Redis 故障时降级：写不进去只记 warn（登出仍然成功），查不到一律当「未拉黑」，
  宁可放过也不误伤正常请求。

**过滤器 vs 拦截器的分工**（这是本版最值得说的一处设计）：

```
请求 → JwtAuthenticationFilter（Servlet 过滤器，Security 链里）
         ├─ 校验签名 / 过期时间
         ├─ 查 Redis 黑名单：已登出的 Token 即使签名有效也不认
         ├─ 查用户：账号不存在或已禁用 → 不认证
         └─ 认证成功 → 写入 SecurityContext（principal = userId，权限 = ROLE_ADMIN/ROLE_USER）
       → UserContextInterceptor（MVC 拦截器）
         ├─ 从 SecurityContext 取 userId + 角色，放进 UserContext（ThreadLocal）
         └─ afterCompletion 里 clear()（Tomcat 线程会复用，不清会串号）
       → Controller / Service：UserContext.requireUserId() 直接拿
```

**过滤器里校验失败不抛异常，只是不写 SecurityContext**。
公开接口带着过期 Token 访问照样能过；需要登录的接口由 Spring Security 统一回 401。
「认证失败」的判断因此只在一个地方，不用每个接口自己判。

另外，过滤器**每次都查一次数据库拿最新角色和状态**，换来的是：
后台改了角色 / 禁用了账号，**下一个请求立刻生效**，不用等 Token 过期。
代价是每个带 Token 的请求多一次主键查询 —— 这个项目里可以接受。

### 2. 商品缓存（穿透 / 雪崩 / 一致性）

```java
// 读
Optional<ProductVO> get(id)
   ├─ 命中真实值             → 直接返回
   ├─ 命中空值缓存(__NULL__) → 抛 PRODUCT_NOT_FOUND（把穿透挡在缓存层）
   └─ miss                   → 回源数据库，然后写缓存（查不到就写空值缓存）
```

- **防穿透**：查不到的商品也缓存一个 `__NULL__` 占位，TTL 5 分钟。
  否则有人拿随机 id 一直刷，请求会全部落到数据库。
- **防雪崩**：真实数据的 TTL = 基础 1800s + `ThreadLocalRandom` 的 0~600s 随机量，
  不会出现「同一时刻大批 key 一起过期、请求同时回源」。
- **一致性**：后台改 / 删商品后直接 `evict(id)` 删 key（**不是更新缓存**）。
  并发下更新缓存容易写进旧值，删掉让下次读自然回源最稳。
- 用 `StringRedisTemplate` + 手动 JSON 序列化，值就是一段可读的 JSON 字符串，
  不引自定义 `RedisTemplate`，也避开 JDK 序列化的兼容问题。
- 所有 Redis 调用点都 try-catch 降级：**Redis 挂了接口照常可用**，只是没有缓存。

商品**列表不走缓存**：条件组合多、命中率低，缓存它性价比不高。

### 3. 前后台分离

**路径规划**（三类权限，写在 `SecurityConfiguration` 的 `authorizeHttpRequests` 里）：

| 范围 | 规则 |
| --- | --- |
| `/api/user/register`、`/login`、`/refresh` | `permitAll()` |
| `GET /api/product/**` | `permitAll()`（商品浏览公开） |
| `/api/admin/**` | `hasRole("ADMIN")` |
| 其它 `/api/**` | `authenticated()` |
| 非 `/api/**`（前端静态资源） | `permitAll()` |

**两层鉴权**：路径级规则挡住请求，`AdminXxxController` 类上的
`@PreAuthorize("hasRole('ADMIN')")` 由 `@EnableMethodSecurity` 在方法入口再拦一道。
两层配合的意义是：**就算以后路径规则漏配了，管理接口也进不来**。

`hasRole('ADMIN')` 要的其实是 `ROLE_ADMIN`，所以过滤器把角色转成权限名时才拼上 `ROLE_` 前缀。

**分页统一契约**：所有列表接口一律 `pageNum` / `pageSize`，由 `PageUtil.start()` + PageHelper 实现，
返回值统一 `PageResult{pageNum,pageSize,total,pages,list}`。
`reasonable=true` 让越界页码自动纠正到首/末页，而不是返回空列表。

**403 必须显式处理**：`AccessDeniedException` 是 RuntimeException，
`GlobalExceptionHandler` 里不单独写一条的话，会被最后的 `Exception.class` 兜底吞成 500。

### 4. 购物车合并

用户没登录时购物车存在浏览器 `localStorage`，登录那一刻一起提交上来：

- 登录接口接受可选的 `cartItems`，在**同一个事务**里合并；
- 另有 `POST /api/cart/merge` 兜底（已登录但本地还残留旧购物车的场景）；
- 合并规则：同商品**数量相加**，统一受库存上限约束；
- 两条容错原则（本地那份可能存了好几天，不能因为一行脏数据让登录失败）：
  商品已删除 / 已下架 / 无库存 → **跳过这一行**；累加超过库存 → **取库存上限**。

### 5. 订单：事务 + 行锁 + 带条件的 UPDATE

**下单**（`OrderService.submit`，一个 `@Transactional` 里五步）：

```
1. 按商品 id 升序 SELECT ... FOR UPDATE 加行锁
2. 持锁逐个判断库存 → 扣减（stock = stock - n，SQL 里再带 stock >= n 兜底）
3. 写订单主表（状态 0 待支付）
4. 写订单明细（商品名/单价快照）
5. 清空购物车
```

- 行锁的作用：并发下单时第二个事务会卡在 `SELECT ... FOR UPDATE` 上等锁，
  等它拿到锁时读到的已经是扣减后的库存，**不会超卖**。
- `ORDER BY id` 很关键：并发事务按同样顺序申请行锁，不会出现循环等待（死锁）。
- 之前只用 `UPDATE ... WHERE stock >= n` 判断+扣减，**没有锁**；
  现在两者都有 —— 行锁保证「先判断后扣减」这段逻辑不被并发穿插，SQL 里的条件再兜一道底。

**状态流转**统一走「带条件的 UPDATE」：

```sql
UPDATE orders SET status = ? WHERE id = ? AND status = ?
```

影响行数为 0 就说明状态已被别的请求改掉（并发点两次取消、重复发货），直接报 409。
这样不用「先 SELECT 判断再 UPDATE」，天然避免并发下的重复流转。

状态机（4 和 5 的区别只是谁发起的，业务上都把库存加回去）：

```
0 待支付 --支付(用户)--> 1 已支付 --发货(后台)--> 2 已发货 --确认收货(用户)--> 3 已完成
0/1 --取消(用户)--> 4 已取消（回滚库存）
0/1 --关闭(后台)--> 5 已关闭（回滚库存）
```

「状态怎么变」只在 `OrderService` 一处实现；「能查到谁的订单」才分前后台
（前台校验归属，越权查别人的订单返回 404；后台不分用户）。

### 6. Vue3 + Element Plus 前端

- **一套 SPA + 两套布局**：`UserLayout`（顶部导航 + 搜索 + 购物车角标）和
  `AdminLayout`（左侧 `el-menu` 侧边栏 + 面包屑），路由 `/admin/**` 需要 `role === 'ADMIN'`；
- **axios 拦截器**：自动带 `Authorization`；响应统一解包 `{code,message,data}`；
  遇到 **401** 自动用 refreshToken 换新 Token 并**重放原请求**（带 `_retried` 标志 + 共享的刷新 Promise，
  不会无限重试也不会并发刷新多次）；刷新失败则清登录态跳登录页；403 提示「无权限访问」；
- **购物车双模式**：未登录存 localStorage，登录后全部走后端接口，登录时自动合并；
- **响应式**：`el-row/el-col` 响应式栅格，宽屏多列、窄屏自动堆叠；
- **订单操作按状态显示**：待支付 → 支付/取消；已发货 → 确认收货；其它状态无操作按钮；
  状态文案优先用后端返回的 `statusText`，本地映射只做兜底。

## 九、已知取舍

- **下单没有收货人 / 电话 / 地址**，`POST /api/order/submit` 仍不带请求体（延续 v1.0 的最小化处理）。
- **支付是模拟的**：没有接支付渠道，`PUT /api/order/{id}/pay` 直接把状态从 0 改成 1，
  只是为了让「已支付 → 发货 → 确认收货」这条链能走通。
- **过滤器每个请求多查一次数据库**（拿最新角色和状态）。换来的是禁用 / 改角色立即生效；
  要省这一次查询，可以把 role/status 缓存进 Redis，或直接信任 Token 里的角色快照，
  代价是「改完要等 Token 过期才生效」。
- **Redis 全量降级**：Redis 挂了黑名单失效（已登出的 Token 又能用）、商品缓存失效。
  演示项目里选择「可用性优先」；生产环境应该把 Redis 当必需依赖，黑名单查询失败时直接拒绝请求。
- **商品删除是物理删除**：历史订单明细存的是快照，不受影响；
  但购物车里引用到已删商品的行会被静默过滤掉（不是报错）。
- **分页仍是 PageHelper**（`pageNum`/`pageSize`），没有引入 Spring Data 的 `Pageable`。
- 前端 `index-*.js` 单包 1.27MB（gzip 410KB），Element Plus 是全量引入；
  要减体积可以改按需引入或 `manualChunks` 拆包。
- 前端只做了构建验证，**没有跑真实浏览器端到端**：
  「登录 → 加购 → 下单 → 后台发货」这条链是在后端接口层验证的，没经过浏览器点击。
1.Jwt退出时 Token 写入 Redis 黑名单，过滤器校验;Refresh Token 机制（短 Token 2h + 长 Token 7d）;拦截器统一解析，userId 放进 ThreadLocal
2.商品模块 + Redis 缓存
商品详情缓存 Redis GET product:{id}，miss 则查 DB 再 SET（TTL 30min）,空值缓存防穿透;查不到的商品也缓存 NULL，TTL 5min;随机 TTL 防雪崩,基础 30min + 随机 0~10min;商品列表加分页（Pageable）
3.前后台分离
前台商品搜索（按名称模糊查）、分类筛选、订单状态流转（取消/确认收货）;后台（Admin）商品 CRUD、订单管理（发货/关闭）、用户管理,接口鉴权;@PreAuthorize("hasRole('ADMIN')") 区分前后台分页所有列表接口加 Pageable
4.购物车/订单优化
购物车合并（登录后把 localStorage 里的临时购物车合并到 DB）
订单创建纳入事务（@Transactional，创建订单 + 扣库存原子操作）
库存扣减用数据库行锁（SELECT ... FOR UPDATE）
5.加入Vue3 + Element Plus 构建响应式页面
